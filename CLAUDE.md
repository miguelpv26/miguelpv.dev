# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Static portfolio site for miguelpv.dev. Plain HTML + vanilla JS + vanilla CSS, no framework, no bundler, no test suite. Two locales (`en/`, `es/`) served as sibling sub-directories; a Cloudflare Worker handles root-path language negotiation.

## Source vs. build

The repository holds **sources only**; `npm run build` assembles the deployable site into **`dist/`** (gitignored, rebuilt from scratch every time). The pages in `en/`, `es/` and `404.html` are source: their `<!-- build:… -->` regions are empty, their `<style id="inline-css"></style>` is empty, and their script tag references the unhashed `main.min.js`. The source `_headers` carries a placeholder CSP hash. Only `dist/` holds the filled-in pages, inlined CSS, hashed bundle and real hash — so a CSS or template change never touches a source page, and git diffs show only real edits. `npm run check` fails if a source page ever contains generated content.

Consequence: the source pages don't render styled on their own. To look at the site, `npm run build && npm run preview` (http://localhost:8080/en/).

## Commands

- `npm run build` — three steps, in order:
  1. **`build:html`** (`scripts/build-html.js`): empties `dist/`, writes every page listed in `data/site.js` into it with its build regions filled (templates, SEO block, JSON-LD, breadcrumb, project facts — see below) and every responsive image's `sizes` generated (see Responsive images), copies `404.html`, writes the blog's Atom feeds (see Sitemap, feeds and redirects), and copies the static files that ship (`assets/img`, `assets/fonts`, `assets/pdf`, both webmanifests, `robots.txt`, `_headers`, `_redirects`, `.well-known/security.txt`), plus `assets/img/favicon.ico` again as `/favicon.ico` for clients that request it without reading the `<link>` tags. **That `STATIC` list is the deploy whitelist**: a new top-level asset directory or root file must be added there or it won't reach production.
  2. **`build:js`**: `scripts/build-js.js` concatenates `assets/js/partials/*.js` (filename order) → terser (drops `console.*`, source map alongside, naming each partial) into `dist/assets/min/main.min.js` → `scripts/fingerprint-js.js` renames it `main.<hash>.min.js` and points every page in `dist/` at it.
  3. **`build:css`** (`scripts/build-css.js`): concatenates `assets/css/partials/*.css` (filename order = cascade order), rewrites `@font-face` URLs to root-absolute, minifies with clean-css, writes a plain fallback before every `color-mix()` / `dvh` declaration (computed from the `:root` tokens; the build fails on a mix it can't resolve, so keep `color-mix()` to `in srgb` with token/hex/rgba/`transparent` stops), **inlines** the result into every page in `dist/`, and writes the strict-CSP `style-src` sha256 into `dist/_headers`. There is no external stylesheet request.
  The steps can run singly (`npm run build:html` etc.), but `build:html` empties `dist/`, so run the full `build` unless you know what you're doing.
- `npm run preview` — `scripts/preview.js`: serves `dist/` like Cloudflare Pages (extensionless URLs, `404.html`, `/` → `/en/`; `_headers` not applied). The server itself is `scripts/serve-dist.js`, shared with `audit-sizes`.
- `npm run check` — `scripts/check.js`, on `dist/` (build first): every page against `data/site.js` (title/description/canonical/hreflang/og tags match its entry; social image exists; article dates agree across site.js, JSON-LD and the visible `<time>`), one `<h1>`, no heading jumps, no duplicate ids, alt on every image, every `<svg>` `aria-hidden` (or `role="img"`), poster/`preload="none"`/label on every video (a hidden slide's poster as `data-poster`), `loading="lazy"` on every hidden image slide, `noopener` on `_blank` plus a new-tab announcement in the link's accessible name (appended to its `aria-label`, else a `<span class="sr-only"> (opens in a new tab)</span>` / `(se abre en una pestaña nueva)` inside it; `mailto:` exempt), valid JSON-LD (every `@id` reference defined on the same page, every date-time zoned), no broken local references (matched case-exactly, as Cloudflare Pages does — Windows and macOS would otherwise hide a wrong case), every `srcset` `w` descriptor is its file's real width and every such `srcset` has a generated `sizes` (no `data-sizes` left over), `_redirects` targets are real pages or shipped files (and no source is still live), each locale's feed lists every article newest first with `site.js`'s dates (and every page links it, its blog hub's visible link points at it, and `robots.txt` names it), every page has the same inlined CSS and a hashed bundle, the `_headers` CSP hash matches the CSS, `security.txt` hasn't expired (warns 30 days ahead — renew `Expires` yearly) — and the source pages are clean (empty regions, unhashed script, and `data-sizes` rather than a hand-written `sizes`). Errors exit 1.
- `npm run deploy` — `build`, then `check` (a failing check stops the deploy), then `scripts/deploy.js`, which zips `dist/` plus a generated `sitemap.xml` into `miguelpv_dev.zip`.
- `npm run og-cards [-- name…]` — renders the social cards (see SEO assets). Not part of `build`.
- `npm run audit-sizes` — `scripts/audit-sizes.js`, on `dist/` (build first): measures every `<picture>` in a local headless Chrome/Edge across viewport widths 320–2560px and fails if a generated `sizes` ever comes out smaller than the width the image is drawn at (see Responsive images). Takes ~2 minutes; run it after any CSS change to a layout that holds images. Not part of `build` or `deploy`.

### Cache busting
The JS bundle is content-addressed: its filename embeds a sha256 prefix of its own bytes, so new code always means a new URL. `_headers` therefore serves `/assets/min/*` as `immutable` for a year, while the HTML stays `max-age=0, must-revalidate`. **Everything under `dist/assets/min/` must be content-hashed** — a mutable, referenced file there would be cached for a year. Never hand-edit the `<script src>` tags; `fingerprint-js.js` owns them (sources keep the unhashed name). Images keep stable names, so `/assets/img/*` is cached for a week plus 30 days of `stale-while-revalidate`, not `immutable`: an image replaced under the same name reaches everyone within a week — rename it if it must change everywhere at once.

Before this existed, `main.min.js` was cached for four hours under a fixed name, so a fresh page could load a stale bundle. That silently broke anything the markup ships `hidden` and JS reveals — most visibly the projects hub toolbar, which simply never appeared. If a deploy ever looks half-applied again, check that the served bundle URL matches the one in the page.

**First-time setup after cloning:** `npm install && npm run build && npm run preview`. There is no lint command and no test runner; `npm run check` is the safety net.

## Architecture

### Language routing
The site has no real "root" page. The Cloudflare Worker at `cloudflare/worker.js` is the only thing that lives at `/`: it reads `Accept-Language`, and 302-redirects to `/en/` or `/es/` (Spanish chosen for `es`, `ca`, `eu`, `gl` when first in the priority list). It sets `X-Robots-Tag: noindex, nofollow` and `Vary: Accept-Language` so the negotiation endpoint is neither indexed nor cached incorrectly. Anything other than `/` falls through to `fetch(request)` (the static assets).

### Pages
Every page exists twice, once per locale, and is hand-maintained: homepage (`en/index.html` / `es/index.html`), projects hub (`en/projects.html` / `es/proyectos.html`), case studies (`en/projects/<slug>.html` / `es/proyectos/<slug>.html`), and the blog (`en/blog.html` / `es/blog.html` + `en/blog/<slug>.html` / `es/blog/<slug>.html`). The 404s are the exception: standalone terminal pages with no header and no footer, not in `PAGES` (`NOT_FOUND_PAGES` in `scripts/site.js` lists them). `en/404.html` and `es/404.html` serve unknown URLs in their locale (Cloudflare Pages serves the nearest `404.html` up the tree), and an English `404.html` at the root serves anything outside the locale folders.

Every page pair is listed once in `PAGES` in `data/site.js`, together with everything about it that isn't content: per-locale `seo` (`title`, `description` ≤155 chars, optional `shareTitle`), the social `card` copy (or a ready-made `image`), its breadcrumb label `crumb`, and for articles `published`/`modified`, `headline` (the full H1) and `keywords`. `PERSON` there holds the author data every page's JSON-LD repeats. The build generates each page's SEO block, JSON-LD, breadcrumb and header from it, the card renderer and the checks read it, and the deploy builds the sitemap from it; `build-html.js` fails if a page in `en/` or `es/` is missing from it. **A page's title or description is edited in `site.js`, never in the HTML.**

To add a blog article: copy an existing one in both locales, add an entry to `PAGES` in `data/site.js` (seo, card, crumb, published/modified, headline, keywords), add a `<li>` to both blog hubs, run `npm run og-cards -- <name>-en <name>-es`, then `npm run build && npm run check`. The JSON-LD dates come from `site.js`, written `YYYY-MM-DD` (or `YYYY-MM-DDTHH:MM`) in Madrid time; `dateTimeFor()` in `scripts/site.js` turns them into the zoned date-times (`2026-07-13T12:00:00+02:00`, noon when no time is given, DST-correct offset) that the BlogPosting and `article:*_time` need, since a bare date gets flagged "datetime property is missing a timezone". `check` fails on any JSON-LD date-time without a zone. Set the article's visible `<time datetime>` elements to the same real days (plain `YYYY-MM-DD`) — Google reads them, and `check` fails if they disagree. Nothing reaches production until `npm run deploy` packages the zip, so unfinished pages can live in the repo without being indexed.

`en/index.html` and `es/index.html` are independent, hand-maintained translations of the same page. Personal info and project metadata in their structured data come from `site.js` (`PERSON`) and `projects.js`, not from the HTML. The PWA manifest is localized per locale: English pages link `/site.webmanifest` (start_url `/en/`, English shortcuts) and Spanish pages link `/site.es.webmanifest` (start_url `/es/`, Spanish shortcuts) — both `scope: "/"`, distinct `id`s. Keep the two in sync when changing app metadata.

### Build regions
`scripts/build-html.js` fills these regions of the source pages (in `dist/` only). **Never write content between `<!-- build:… -->` markers in a source page** — change the template or data and rebuild; `check` fails on a non-empty region in a source.

- **Page-wide, from `templates/`:** `head` (charset, viewport, theme colour, font preloads, favicons, manifest), `seo` (title, description, author/robots, canonical, hreflang, the locale's feed link, Open Graph incl. `article:*` dates for articles, Twitter — all from the page's `site.js` entry; `og:type` is `website` for the homepages and hubs, `article` under them; og/twitter descriptions are the meta description), `header` (skip link + header + main `<nav>`) and `footer`. Placeholders are `{{name}}` for per-page values (`prefix` for the `../` depth, `title`, `logoHref`, `projectsCurrent`, `enHref`, `year`, …; text values are HTML-escaped) and `{{t.key}}` for per-locale copy from the `STRINGS` table in `build-html.js`. Page-specific head additions go after `<!-- /build:head -->` (the homepages preload their hero image there).
- **Generated in code:** `jsonld` (in `<head>`; `scripts/jsonld.js` builds the page's whole `@graph`: the same WebSite, Person and profile image on every page; the page node — a ProfilePage (`mainEntity` the Person) on the homepages, CollectionPage + ItemList on the projects hub, CollectionPage + Blog (whose `blogPost` lists every article, each the same BlogPosting node the article page carries) on the blog hub, WebPage on case studies, WebPage whose `mainEntity` is the BlogPosting on articles, plus the same Blog node the hub has, so the post's `isPartOf` resolves on the page — every `@id` reference must resolve within its own page, since Google doesn't follow them across pages; a BreadcrumbList, referenced only from the WebPage/CollectionPage, since schema.org defines `breadcrumb` nowhere else; and the schema entity of every project the page has a `build:project-*` region for, from `projects.js` `schema`) and `breadcrumb` (the visible `<nav class="breadcrumb">`, built from the same trail as the JSON-LD: Home → section → the page's `crumb`).
- **Project facts, from `data/projects.js`:** `<!-- build:project-card SLUG -->` (a hub card's opening `<article>` with the filter data `07-project-filters.js` reads: `data-tags` = category + tags, `data-updated`, `data-ongoing` for open-ended years; alternate cards get `project-card--reverse`), `project-meta SLUG` (the hub's role · years · #category · status line), `project-tags SLUG` (toggle buttons on the hub, plain labels elsewhere) and `project-facts SLUG` (a case study's role · years · status line; with `terminal` — `<!-- build:project-facts biglo terminal -->` — the same facts as `<dt>/<dd>` rows inside a terminal manifest). A project's role, years, category, status or tags are edited in `projects.js`, along with tag/category/status labels per locale. A project's JSON-LD entity is its `schema` there (`null` = this site itself). Descriptions, bullets, media and case studies' detailed stack lists (deliberately richer than the hub tags) stay hand-written.

The build keeps each file's line endings.

### Responsive images
Every screenshot and photo is a `<picture>`: an AVIF `<source>` and a WebP `<source>`, each with a `w`-descriptor `srcset`, and a PNG `<img>` fallback whose `<picture data-fullres>` is what right-click opens. **The source pages never carry `sizes`.** Each `<source>` names the layout it sits in (both sources of a picture the same — `check` enforces it) — `data-sizes="hero"`, `case-study`, `home-card`, `hub-card` or `about` — and `build-html.js` writes the exact `sizes` from `IMAGE_LAYOUTS` in `data/images.js` and the image's real aspect (read from its widest candidate). The table restates the CSS as formulas per viewport range (box width as `vw`·viewport + `px`, box height ÷ width), because the right value depends on both the box and the image's shape: a portrait screenshot in a 16:9 `contain` box fills only part of it, a 4:3 photo in the square `cover` box spills past it. Every length is rounded up. `home-card` assumes the homepage shows three teasers (its grid gains a column at 1168.89px).

The homepages preload the hero (the LCP image) with `<link rel="preload" as="image" type="image/avif" imagesrcset="…" data-sizes="hero">` — no `href`, so a browser without `imagesrcset` support skips the preload instead of fetching a file the picture won't use. The build gives it the same value as `imagesizes`, and `check` fails unless its candidates and sizes equal the hero `<source>`'s exactly: any difference means the browser preloads one file and the picture fetches another. Change both together.

**A CSS change to padding, gaps, column splits, aspect ratios or breakpoints around images means updating `IMAGE_LAYOUTS`**, then `npm run build && npm run audit-sizes`. The audit is the only thing that ties the table to the real layout.

Candidate ladders: screenshots `-320w`, `-640w`, `-960w`, `-1280w` and the full-size `<name>.avif` (a case-study slide is drawn up to 1296px wide); images narrower than that stop at their native width (`-753w`, `-560w`…). The About photos stop at `-1400w` (the widest any screen draws them), not at their multi-megapixel masters. The hero is `picture.avif` (468w) and `picture-702w.avif`: `picture.png` is a cutout of `picture.jpg` scaled by 1/1.5 with 32px of transparent canvas on top, so the 702w rung is the JPG at full size on a 702×848 canvas (JPG at y=48) with the PNG's alpha upscaled 1.5×, and edge pixels un-mixed from the JPG's white backdrop (F = (C − (1−a)·255)/a, the PNG's own colour where a < 0.1). List candidates narrowest first; `check` verifies each descriptor against the file. The WebP ladder mirrors the AVIF one (`X-640w.avif` → `X-640w.webp`, same widths), minus any rung that weighs as much as a wider one — at native width lossless WebP is often tiny, so e.g. `mit-license` serves 320w and 900w only; the browser then takes the wider, lighter file. WebP rungs are encoded at the lowest lossy quality (q50–90, `smartSubsample`) that reaches their AVIF twin's PSNR, capped at q90 (WebP's subsampled chroma can't match 4:4:4 AVIF on coloured text), or lossless when that's smaller. Like ffmpeg, an image encoder is deliberately not a dependency; the current files were made with sharp (libvips/aom) in a scratch folder, resized with lanczos3 from the PNG master: AVIF, `chromaSubsampling: '4:4:4'`, `effort: 9`, at the lowest quality (never below 40) whose PSNR against the master matched or beat the file it replaced — in practice 40–50 for screenshots (50 for the new `-1280w` rungs and the hero), 40–70 for photos. 4:4:4 matters: the old 4:2:0 encodes smeared coloured text.

### Icons
The SVGs are the masters; every raster icon is rendered from one, so they can't drift (they once did: `favicon-manifest.svg` drew the `</>` at 90% of the width while everything else drew it at 81%). One glyph, one transform: `favicon.svg` (black circle — tab icon and header logo), `favicon-no-bg.svg` (the hub's logo panel) and `favicon-manifest.svg` (black square) all draw it at 80.9% width, centred; `favicon-maskable.svg` draws it at 71.9%, so its farthest pixel sits at 36% of the size from the centre, inside the 40% circle Android may crop a maskable icon to. From `favicon-manifest.svg`: `favicon-96x96.png`, `apple-touch-icon.png` (180), `favicon-192x192.png`, `favicon-512x512.png` (also the JSON-LD logo) and `favicon.ico` (16 + 32px PNG frames); from `favicon-maskable.svg`: `favicon-maskable-192x192.png` / `-512x512.png`; from `laptop-code.svg` / `envelope.svg`: the 96px shortcut PNGs. All opaque (flattened onto black — iOS and Android expect opaque app icons), lossless, rendered at 8× and downsampled with lanczos3 (sharp, from a scratch folder, like the image encodes). The manifests list the PNGs with exact `sizes` and the SVGs as `sizes: "any"` extras: Chrome's install criteria want 192 and 512 icons, and SVG manifest icons aren't supported everywhere. `check` verifies every manifest icon exists, PNG sizes match their declared `sizes`, the 192/512 `any` and `maskable` PNGs are present, and both manifests list the same icons. Every page (404s included) links the 180px `apple-touch-icon.png`.

### Client JS (`assets/js/partials/*.js`)
One classic script (no modules) cut into ordered partials, like the CSS: `01-utils.js` (`debounce`, `safeInit`, `prefersReducedMotion`), one file per feature (`02-mobile-menu.js` … `07-project-filters.js`, each holding its own constants — `MOBILE_BREAKPOINT_PX` in the menu, the slider's `I18N` strings in the slider), and `08-init.js`. They share one top-level scope, so functions can sit in any file, but a top-level `const` doesn't exist until its file has run: **`08-init.js` must stay last**, as the only file that starts anything. A new partial is picked up by the build with no other step. `initApp()` runs six features under `safeInit` wrappers:
- `initMobileMenu` — button-driven nav drawer at `≤1276px`, manages `aria-expanded`/`aria-hidden`/`inert`, body scroll lock on `html` (the scroll container), focus containment while open (every `<body>` child except the header goes `inert`), focus restore, and overlay click.
- `initMatrixEffect` — canvas animation on `#matrix-canvas`. Honors `prefers-reduced-motion` (early return), DPR-clamped to 2, pauses naturally via the trailing fade.
- `initSliders` / `createSlider` — generic slider for any `[data-slider]` block with `[data-slide]` children and `[data-slide-prev]`/`[data-slide-next]` controls. Lazy-initialized via `IntersectionObserver`; supports per-slide `data-duration` (seconds, clamped 1–60), `<video data-slide>` slides, dot indicators (auto-created, `aria-controls` → slide ids namespaced per slider as `slider-N-slide-M`), a pause/play toggle (WCAG 2.2.2; first in the slider's tab order, in one centred bottom row with the dots; it pauses the shown video too, and `prefers-reduced-motion` starts it paused), ARIA live announcements of slide changes the visitor makes (the slide's `alt` or `aria-label` — the auto-advance stays silent), keyboard nav (←/→/Home/End), and a temporary hold on hover/focus/hidden tab that, unlike the toggle, lifts by itself. Videos `loop`, so they never fire `ended`: set a video slide's `data-duration` to the clip's length. Every video ships `preload="none"`, a `poster` (`<name>-poster.webp` next to the clip) and an `aria-label` in the page's language. ffmpeg is deliberately not a project dependency (an ~80 MB binary for a rare, one-off job); encode new clips with any ffmpeg build, using the settings the current ones were made with:
  ```bash
  ffmpeg -i raw.mp4 -an -c:v libx264 -preset veryslow -tune animation -crf 22 -pix_fmt yuv420p -movflags +faststart clip.mp4
  ffmpeg -i clip.mp4 -frames:v 1 -vf "scale=min(960\,iw):-2" -c:v libwebp -quality 80 clip-poster.webp
  ```
  Screen recordings compress enormously at these settings (a 6.8 MB recording came out at 152 KB, visually identical); `-an` drops the audio track the muted slider never plays.

  **Nothing hidden in a slider downloads with the page.** Slides are stacked in one box, so a lazy image under the shown one counts as "near the viewport" and loads at once; on the homepage that put ~280 KB of slides in competition with the hero (mobile Lighthouse 88 → 97 once fixed). So: until `initSliders` marks a slider `data-slider-initialized` (50px before it scrolls in), its hidden slides are `display: none` (`07-slider.css`); every hidden image slide is `loading="lazy"`; a hidden video slide carries `data-poster` instead of `poster` (a poster attribute always downloads immediately) and `createSlider` sets the real one when it starts — `check` enforces the last two. The first (`.active`) slide gets `loading="lazy"` too when its slider starts below the fold at every viewport (all the homepage sliders, the hub's Biglo card, the Biglo case study); it stays eager where it can be in the first screen (the other case studies' sliders, the hub's first card). A first slide that's a video keeps a real `poster`, since without JS it's all that shows. `audit-sizes` overrides the `display: none` so it still measures every slide.
- `initContextMenuHandlers` — right-click on `picture[data-fullres]` opens `data-fullres` in a new tab; right-click on `video[data-slide]` opens its `src`.
- `initProjectCardLinks` — makes a project card's media thumbnail follow the card's link (the media sits above the stretched-link overlay so its right-click handler keeps working).
- `initProjectFilters` — search / tag chips / last-activity sort on the projects hub; the toolbar ships `hidden` and JS reveals it; state mirrored into `?tag=` / `?q=`.

All features degrade silently if their root elements are absent. Console statements are stripped by terser's `drop_console`, so feel free to leave `console.warn`/`info` calls in source.

### Styles (`assets/css/partials/*.css`)
Authored as ordered partials (`01-tokens.css` … `15-responsive.css`), concatenated in **filename order — which is the cascade order, so renumber with care**. (`11-blog.css` must load after `10-case-study.css`, whose shared prose rules it refines.)

The blog article's **prose spine** — the numbered `## ` sections, disc lists and inline-code chips — is deliberately *not* duplicated: `10-case-study.css` defines those rules against `.case-study__section, .article__section` together. A case study and an article are the same kind of document, so they must not drift apart. `11-blog.css` holds only what the blog doesn't inherit (post list/cards, the deck, the draft banner, related reading); tag pills reuse `.project-tags .tag`. Design tokens live in `:root` in `01-tokens.css`. Inline middot separators are the drawn `<span class="sep-dot" aria-hidden="true"></span>` (`03-base.css`), never a typed `·` — a glyph is text to contrast checkers and copy-paste — with whitespace around it wherever the neighbouring words would otherwise run together. Uses BEM-ish class names (`header__container`, `nav__item`). Mobile breakpoint is `1276px` and must stay in sync with the `mq` in `initMobileMenu`. The CSS is inlined into every built page under a strict CSP whose hash the build recomputes, so any CSS change must go through `npm run build`.

### Sitemap, feeds and redirects
The blog has one Atom feed per locale, `/en/feed.xml` and `/es/feed.xml`, written at build time by `scripts/feed.js` from `PAGES`: every page with `published` becomes an entry (headline, meta description as the summary, the `site.js` dates), newest first, so a new article joins the feed with no extra step. Every page links its locale's feed in the SEO block (`<link rel="alternate" type="application/atom+xml">`, how feed readers find it), `robots.txt` lists both as sitemaps (Google and Bing accept Atom there, and it points them at what's new), and each blog hub shows a visible "Atom feed" link under its intro. They're served as plain XML, not `application/atom+xml`: some browsers download that type instead of showing it, and feed readers don't care.

`sitemap.xml` is generated at deploy time by `buildSitemap()` in `scripts/deploy.js` from `PAGES` in `data/site.js`: both locales' `<url>` entries and their reciprocal `hreflang` alternates are derived from each entry. `<lastmod>` is the date of the last commit touching that page's **source** file, or today if it has uncommitted changes — accurate, since CSS and template changes never touch sources. The root `/` is deliberately not listed (it's a `noindex` 302). URL renames get a 301 line in `_redirects` (`check` verifies its targets).

### SEO assets
Meta descriptions stay ≤155 characters (`check` fails above 160). There is no `keywords` meta — search engines ignore it. Each non-home page has its own 1200×630 social card at `assets/img/og/<card.name>-<locale>.png` (homepages give a ready-made `image` in `site.js`: `assets/img/og/home-en.png` / `home-es.png`, made by hand); the generated SEO block references it in `og:image` (+ `:type`/`:width`/`:height`/`:alt`, the alt derived from the card copy) and `twitter:image(:alt)`, and an article's generated `BlogPosting` `image` points at the same file (`check` verifies). The cards are rendered, not hand-drawn: `npm run og-cards [-- name…]` (`scripts/og-cards.js`) fills `templates/og-card.html` with each page's `card` copy from `site.js` and screenshots it with a local headless Chrome/Edge (`BROWSER_PATH` overrides discovery), using the site's own subset fonts — so card copy can't use glyphs the subset lacks (write `->` and `~`, not `→` and `≈`). A new page needs a card in both locales. There is no microdata (`itemprop`) — structured data is JSON-LD only.

## Conventions

- Sources are `en/`, `es/`, `404.html`, `templates/`, `assets/` (js, css partials, img, fonts, pdf), `data/` (`site.js`, `projects.js`, `images.js` — the image layout table), `.well-known/` and the root config files. `data/` holds no code: the scripts read it through `scripts/site.js` and `scripts/images.js`, which re-export it next to their helpers (`DIST`, `NOT_FOUND_PAGES`, `fileFor`, `dateTimeFor`, `imageFor`; `sizesFor`, `imageSize`).
- `assets/img/` keeps only icons at its root (favicons, manifest icons, shortcut icons, `sprite.svg`); photos and screenshots live in `hero/`, `about/`, one folder per project slug, `blog/`, and every social card (homepages included) in `og/`.
- Spanish copy uses Spanish punctuation: an aside opens with ` —` and closes with `— ` (raya attached to the aside, space outside); a raya that only separates a label from its description (`<strong class="lead-in">X</strong> — …`, link titles like "Biglo — caso práctico") keeps a space on both sides. `dist/` is output: never edit it, never commit it.
- Any user-facing copy change requires editing both locales' version of the page (or the per-locale strings in `site.js` / `projects.js` / `STRINGS`).
- JSON-LD structured data, OpenGraph tags, and `sitemap.xml` are part of the deployable; keep them consistent with the visible content. Run `npm run build && npm run check` before committing.
