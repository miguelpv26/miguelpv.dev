When a framework
earns its weight

Vue, React or plain HTML: how I chose on four real projects.

I've built a Vue app on my own, worked on a large React one as part of a team, and built this site and a client's site with no framework at all. Each time the choice came down to the same question, and it was never "which framework is best". It was: how much of this page has to live in the browser, and who pays for it? This is how I answered it, project by project.

Start from what the page does

Before I think about a stack, I sort the page into one of two kinds. Some pages are for reading: content, a few interactions, often a single visit that started on a search engine. Others are for using: someone signs in, moves between views that share the same data, and stays a while.

This site is the first kind. Everything on it that moves comes down to six small features: the mobile menu, the matrix animation behind this text, the image sliders, right-click to open an image at full size, the clickable project cards and the filters on the projects page. All of that ships as one script of 13.1 KB, 4.7 KB once compressed. The rest is HTML that's already there when the page arrives, so there's nothing for a framework to manage.

That's how I think about frameworks: they're tools for keeping state in sync across a page. When a page has almost no state, the framework has nothing to do, and the visitor still downloads it.

Where it earned it: Biglo

Biglo is the second kind of page from end to end. It's a B2B logistics platform with three kinds of user (companies looking for space, warehouse owners and logistics operators), sign-in, an interactive map, availability calendars, service requests and two languages, all sharing the same data across many views. I built it on my own. Doing that without a framework would have meant writing my own, smaller and worse.

I chose Vue, for three reasons:

  • One toolkit, from one team. Routing (Vue Router), shared state (Pinia) and translations (vue-i18n) all come from the Vue team and are built to work together. With React I'd have had to pick each of those myself and keep packages from different authors in step. When you're the only developer, every decision you don't have to make is time back.
  • I already knew it. With a three-sided marketplace to ship alone, the framework I'm fastest in beat any that might have been slightly better on paper.
  • Less work to keep it fast. Vue tracks which data each part of the page depends on and updates only what changed, so I didn't have to tune re-renders by hand. That's exactly the work I spent time on later, in a React codebase.

And it still scored 100 in all four Lighthouse categories. The framework didn't cost the score: splitting the code by route did most of the work, so each screen downloads when someone opens it, not with the home page. A framework doesn't make a site slow. Shipping all of it on the first load does.

When it isn't your choice: Digitalando

Most of the time you don't choose the framework, you join it. Digitalando was a large platform with many modules and a team already writing React when I joined as a frontend developer, in its final months. There, React wasn't just a library. It was the language the whole team shared, and that's worth a lot on its own.

So the question changed from "which framework?" to "how light can I keep this one?". I lazy-loaded the heavy modules, removed unused libraries and dead code, fixed components that re-rendered for no reason and optimized the images. The landing page's LCP went from 6.7s to 3.2s.

3.2s still isn't good: Google's threshold is 2.5s. What was left wasn't React. It was a background video the landing page was built around, and the analytics and consent tags the business ran on, and leaving React wouldn't have fixed either. Inside a framework, discipline matters more than the framework: most of what I removed was code and assets someone had added, not the runtime.

The platform is offline now, but my notes on it are on GitHub (opens in a new tab).

Where it didn't: a client's website

Abogada de la Tierra is a law firm in Alicante, and its website is a page for reading: who they are, what they do and how to get in touch. I built it the same way as this site: no framework, no runtime dependencies, the critical CSS inlined at build time and a serverless contact form.

What the client doesn't see, but still gets:

  • Nothing to upgrade. No new major version of a framework to migrate to, and no dependency tree to audit and patch every few months. The site will keep working as it is for years.
  • Cheap to host, easy to hand over. Static files and one small form function (5 KB, running on Cloudflare, never downloaded by the visitor), with no server to keep running.

The middle ground: Nuxt and Next

Some projects are both: an app people use, with pages people need to find through search and see quickly on a first visit, like public listings, a landing page or a blog. That's what Nuxt (for Vue) and Next (for React) are for. They render the HTML on the server or at build time, and the framework takes over in the browser afterwards.

Biglo got there. At one point we discussed moving it to Nuxt, for SEO and performance: a Vue single-page app shows search engines and first-time visitors an empty page until its JavaScript runs, and rendering the HTML first fixes both. Nuxt rather than Next because we already had Vue. That didn't decide it for us, since we could have gone to Next, but Nuxt kept our components, our store and everything we already knew, so the migration would have been far simpler. Unless you have a reason not to, take the natural step.

We agreed it was the right move, and we didn't make it. There were other priorities: improving Biglo's own search for spaces and services, plus work already underway on CORS, a CDN for the images and trying out Redis for caching. We went one step at a time, and server rendering wasn't the main problem then. Knowing which tool fits best doesn't mean switching to it today.

So I haven't shipped Nuxt or Next in production yet. When I do, it'll be for that reason: an app whose pages also have to rank and load fast.

The questions I ask

When a new project comes in, these are the questions I go through, in this order:

  • Will people mostly read this page, or use it? If they read it, I don't use a framework.
  • Does the same data need to stay in sync across several views? If it does, a framework will do that better than I would by hand.
  • Does it also need to rank, or show up fast on a first visit? Then Nuxt or Next, or static pages next to the app.
  • Is there already a team or a codebase? Then the framework is chosen, and my job is to keep it light.
  • Who looks after it once I've handed it over? If it's a client with no developer, as few dependencies as possible.

Two things would change my answer. A site that starts as pages to read but is clearly going to become an app: there, starting with a framework is cheaper than migrating later. The framework itself isn't the expensive part. The bytes the visitor downloads and the upkeep afterwards are. I use one when it does work I'd otherwise do worse by hand, and not before.

fun fact: no framework still has a build

The nerdy bit. This site has no framework, but it does have a build step. A script joins the JavaScript files, minifies them and puts a hash of their content in the file name, so browsers can cache it for a year and still get new code the moment it changes. It also inlines the CSS into every page and computes the hash the Content Security Policy needs to allow it. Vanilla means nothing extra runs in the visitor's browser. It doesn't mean no tooling.
